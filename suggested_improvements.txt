Suggested improvements for public package API classes

Scope:
- This file lists non-implemented recommendations only.
- Focused on ConfigParams, Dataset, and MergeMethods.
- Includes style, naming, consistency, correctness, robustness, and packaging concerns.

==================================================
Class: ConfigParams
==================================================

1. Validate numeric types explicitly in __init__
- Current checks enforce ranges but do not enforce integer semantics.
- Add explicit type checks for reg_lmax, win_lmax, and win_eff_lmax (e.g., reject floats/bools).

2. Validate finite coordinate values
- lon_bounds and lat_bounds range checks exist, but finite-number validation is not explicit.
- Reject NaN/Inf bounds to avoid downstream failures in masking logic.

3. Clarify and centralize longitude convention
- Current implementation enforces lon in [0, 360] only.
- If package users may provide [-180, 180], either normalize internally or document strict [0, 360] requirement in one authoritative place.

4. Improve API ergonomics for this pure config container
- Consider using a dataclass to simplify initialization and representation.
- This would also make defaults/immutability options clearer for package users.

5. Add class-level documentation for units and conventions
- Document expected depth unit conventions and longitude convention used by downstream classes.
- Include whether bounds are inclusive and any assumptions about coordinate ordering.


==================================================
Class: Dataset
==================================================

1. Public API naming consistency
- Public constructor arguments and methods still use camelCase naming (filePath, modelType, getDataset, etc.).
- For package-facing consistency, prefer snake_case API (with compatibility aliases if needed).

2. Overly broad and unused imports
- Module still imports many unused packages (examples: yaml, pyshtools, sys, pandas, netCDF4, pdb, Model1D, RectBivariateSpline).
- Remove dead imports to improve maintainability and import performance.

3. getInterpolationParameters edge cases and grid construction
- depths is typed as list[int], but practical inputs can be float-valued depth knots.
- target_reg_increment is floor-cast to int, which may under-resolve target grids.
- np.linspace(-180, 180, N) includes both endpoints; verify whether duplicate seam handling is intended.

4. assign_names can still rename ambiguous variables
- It checks self.dataset.variables, which mixes data variables and coordinates.
- Consider coordinate/dimension-first detection to avoid accidental renames when data variables share alias names.

5. convert_units idempotency and unit tracking
- Unit conversion can be applied repeatedly if caller invokes convert_units("m") multiple times.
- Consider tracking current depth/velocity units in metadata and guarding against double-scaling.

6. plot_variable and plot_all_variables rendering control
- plot_variable may call plt.show() for created figures, and plot_all_variables may show again.
- Centralize show/close behavior in one layer to avoid duplicate rendering and improve batch plotting behavior.

7. save_model path/permission validation and error surfacing
- save_model currently validates only None path.
- Add parent-directory existence/permission checks and wrap write errors with clearer context.

8. Exception specificity and user-facing messages
- Some errors are still generic and do not always include actionable context.
- Improve exception messages to include parameter names, expected values, and received values.

9. Tighten typing and return annotations across public methods
- Several methods still miss precise return types and broader input abstractions.
- Use explicit return annotations and collections.abc.Sequence where appropriate.

10. Add tests for key failure modes and plotting behavior
- Add targeted tests for coordinate-name detection ambiguities, interpolation seam behavior, unit-conversion idempotency, and plotting show/close control.


==================================================
Class: MergeMethods
==================================================

1. Public API naming consistency
- Methods and constructor arguments still use camelCase patterns in a Python package context.
- Standardizing to snake_case would align with ecosystem conventions.

2. Overly broad and unused imports
- Module still includes unused imports (examples: multiprocessing, os, concurrent.futures, time, sys, yaml, pandas, pdb).
- Removing these reduces maintenance overhead and import noise.

3. Exact float depth matching remains brittle
- Depth access still uses exact .sel(depth=float(depth)) in reshape_field and create_window call sites.
- Use nearest selection with tolerance to avoid KeyError from floating-point coordinate mismatch.

4. Debug side effects remain in core merge flow
- apply_window/process_slice generate hard-coded plot files during normal execution.
- Move debugging plots behind an explicit flag or logger-level control to avoid unexpected I/O in library usage.

5. merge implementation/comment drift
- Comments mention thread/process strategy considerations, while merge runs strictly sequentially.
- Align comments with current behavior or reintroduce controlled optional parallel execution.

6. Output variable naming consistency
- write_model emits name="dv", then merge renames to dataset variable "merged".
- Define and document a single consistent output naming contract (or make it configurable).

7. Strengthen typing/contracts for helper methods
- Add explicit type hints and return contracts for arrays, SH objects, and xarray structures in helper methods.
- This improves discoverability and static-analysis quality for package users.

8. Add targeted tests for merge boundary conditions
- Add tests for unsupported config combinations, depth-coordinate mismatch tolerance behavior, all-NaN slice handling, and debug-plot side-effect controls.


==================================================
Cross-class/API publication recommendations
==================================================

1. Define and document public API surface
- Explicitly mark internal helpers as private (leading underscore) and keep stable, documented public entry points.

2. Standardize naming strategy across classes
- Choose one public naming style (preferably snake_case) and provide compatibility aliases during transition.

3. Centralize unit and coordinate conventions
- Keep one authoritative source for depth units and longitude conventions to prevent behavior drift across classes.

4. Keep top-level imports lightweight
- Delay plotting/spherical-harmonic dependencies until needed to reduce import-time burden for non-plotting workflows.

5. Expand package-level test coverage before release
- Add smoke tests for end-to-end merge and focused unit tests for validation, interpolation, windowing, depth selection tolerance, and output contract stability.
